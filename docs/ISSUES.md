# 発見された問題と対応の記録

開発中に見つかった問題を、原因・対応・検証とともに残す。未解決のものも隠さず載せる。

## 1. 表記揺れ検出が時制語尾の交替を「揺れ」と誤認した（修正済み）

- 発見: 開発シード0の出力で、語末 ga↔mu・ge↔mi が表記規則として受理されていた
- 原因: 「2つの語形が同じ文書に共起しない」だけを根拠にしていた。年代記は過去形、法文は未来形というように、時制語尾も記録の種類ごとに偏るため同じ統計になる
- 対応: 「その文字自体が現れない文書群が存在し、交替形がそこに集中する」という全体検定に変更。語端だけの2文字以上の交替は接辞の可能性が高いので除外
- 検証: tests/test_decipher.py::test_normalizer_keeps_morphological_alternation_apart。開発シードで統合の適合率 0.87→1.00

## 2. 表記揺れの統合の再現率が低い（0.25〜0.6）（修正済み）

- 発見: 開発シード0〜2の採点。数詞の方程式で zu/tsu の未統合形が未知数を増やし、解が決まらなかった
- 原因: 対になる語形が両方とも出現した場合しか統合していなかった。また書記が5%の語で習慣を外すため、単純な文書共起の検定が通らなかった
- 対応: 受理した交替を「全文書に規則を適用した形」へ全語一括で書き換える方式に変更。検定は文書内の混在度に変更
- 検証: 開発シードで KES の再現率 0.63→1.00、SOT 0.29→0.89

## 3. 採点器の位置対応の誤りで、正しい分割が誤りと数えられていた（修正済み）

- 発見: 誤答例の一覧に godo|zu（正解）と godo+tsu（予測）のように同じ分割が並んでいた
- 原因: 正規化形と原表記の長さが違うとき、形態素境界の位置を原表記に戻す対応表がずれていた
- 対応: difflib の編集操作（opcodes）から対応表を作るように変更
- 検証: KES シード0の境界適合率が 0.84→0.99（解読器は不変、測定の誤りだった）

## 4. 1形しか現れない語幹の処理が屈折語の語根を切り刻んだ（修正済み）

- 発見: SOT で語根 faedem が faed+em と分割されていた
- 原因: 「信頼できる接辞で終わる語は切る」処理を語幹にも再帰的に適用していた。融合語尾の言語では語尾は1つしか付かない
- 対応: 内側への再帰は、実際に連鎖として観測された接辞の組に限る
- 検証: SOT シード0の境界適合率 0.75→0.98

## 5. 形態素解析が「切らない」という選択肢と比較していなかった（修正済み）

- 発見: 単体テスト test_morphology_finds_suffix_paradigm が kamir を kami+r と分割して失敗
- 原因: 分割候補どうしだけを比べ、語全体を語幹とする解釈を候補に入れていなかった。複合語尾 lar の末尾 r が接辞に見える入れ子の断片を拾った
- 対応: 語全体が語幹として同等以上の語尾を説明する場合は切らない
- 検証: 同テストが通過。UMB の境界F1 0.48→0.64

## 6. 接頭辞型の言語で語根が「語尾」として切り出された（修正済み）

- 発見: UMB の誤り一覧で nguu|kanufa が nguuk|anufa と分割されていた
- 原因: 常に接尾辞側を先に解析していた。接頭辞型では接頭辞が「語幹」、語根が「語尾」に見える
- 対応: 両側を独立に解析して、支持の大きい側を先に確定する
- 検証: UMB の境界F1 0.64→0.76〜0.87（開発シード0〜4）、品詞正解率 0.7→0.9

## 7. 数詞の方程式から、繰り返し現れる数詞が落ちていた（修正済み）

- 発見: 方程式を正解値で検算すると、15本中10本が成り立たなかった
- 原因: 文書内の定型語（品目名など）を除く処理が、多くの行に現れる数詞（「二十」など）まで除いていた
- 対応: 数詞候補は合計行から全体で決め、文書ごとの定型語判定では除かない
- 検証: KES LEVEL C で数詞20語すべて正解

## 8. 合計行に一度も現れない数詞が候補から漏れ、式が全部ずれた（修正済み）

- 発見: 開発シードの一覧で UMB・SOT の失敗がすべて「候補漏れ」と対応していた
- 原因: 数詞候補を合計行の語だけから取っていた
- 対応: 形成要素の基体を候補に加える。さらに、品目名の決まった側に隣接する語を数詞とみなす位置補完を、厳しめ・緩めの2通りで試して多くの式を満たす方を採る
- 検証: 開発30ケース中、解けた数 14→25、誤った値を含む解 4→ほぼ0

## 9. 欠損のある文書の式が偽の解（巨大な整数）を生んだ（修正済み）

- 発見: SOT で値が 1096, 1987, … という解が「解けた」と報告された
- 原因: 欠損で数詞が欠けた式を、系がまだ決まりきらない段階で受理していた
- 対応: 欠損のない式を先に入れ、欠損のある式は順序を無作為化した合意で選ぶ。最小単位が1でない解・満たす式が少ない解は棄却して「判定不能」と報告
- 検証: tests の数詞テストと開発シードの一覧。誤った値を自信ありで報告するケースが消えた

## 10. 20進法で加法（十＋三）と乗法（三×二十）を同時に仮定しないと解けない（修正済み）

- 発見: UMB LEVEL C が5シード中4シードで未解決
- 原因: 形成要素の仮説を1つずつ独立に試していたため、片方だけでは系が決まらなかった
- 対応: 全形成要素に加法を仮定した状態から、1つずつ他の仮説（なし・乗法×2〜150）と入れ替えて比べる
- 検証: UMB LEVEL C が5シード中4シードで解決

## 25. 独立初見テストで数詞がすべて判定不能だった（合計行の仮定が外れた）（修正済み）

- 発見: 独立初見テスト gpt6-blind-01（v1.0.1、正解公開前の最初の試行）。数詞14語がすべて判定不能
- 原因: 数詞ソルバーが「会計記録には合計行がある」という仮定に全面的に頼っていた（限界として明記済みの仮定）。この言語には合計行がなかった。対訳が30文あったのに、数量の手がかりを使えていなかった
- 対応: v1.1: 合計行がない場合、対訳の数量を概念 #NUM として対応付けに混ぜて数詞候補を見つけ、対訳の文ごとに方程式を立てる。gpt6-blind-01 は方向を決めるのに読んだだけで、調整・検証には使っていない
- 検証: 生成器に合計行なしの条件を追加し、開発シード20個で検証: 合計行なし LEVEL A の数詞正解率 0.004 → 0.227、誤答率 0.009

## 26. 対訳だけの少ない式では、誤った倍数の仮説が選ばれた（修正済み）

- 発見: v1.1 の開発中。「十」を「3倍」と判定し、信頼度0.98のまま数詞9語を誤答
- 原因: 仮説を「満たした式の数」で比べていた。この数は値を多く決める仮説ほど増えるので、誤った仮説が有利になる
- 対応: 「矛盾した式の数」で比べ、区別できなければ決めない。さらに、位取りの単位は掛けられる語より大きいという一般的な性質を制約に加えた（解読器の新しい仮定）
- 検証: 開発シード: 誤答した数詞が約30件から7件に減少

## 27. 値が少ないときに誤った基数（2進法・3進法）を主張した（修正済み）

- 発見: v1.1 の開発中。{1,2,4,6} の値から「2進法」と判定
- 原因: 基数の判定が「b以上の値がすべてbの倍数」だけを見ていた
- 対応: b ≥ 4 で、1〜(b−1) がすべて揃うときだけ基数を主張する
- 検証: tests/test_decipher.py::test_base_is_not_claimed_from_few_values

## 28. 欠損が数詞を消したかどうかを行の形から判定する方法は効かなかった（未解決）

- 原因: 「数詞は無事」と判定した式の31%で実際には数詞が欠けていた。数詞の候補から漏れた語を人名などと数えてしまう
- 対応: 変更を取り消した（v1.1 には含めない）。混入率を数%に下げる方法は未発見
- 検証: 開発シード24ケース: 数詞正解率 0.363 → 0.219 に悪化したため不採用

## 29. 合計行がないとき、対訳の式の合意型の解法が働いていなかった（修正済み）

- 発見: Codex の自動レビュー（PR #3）
- 原因: 対訳の式を固定順の式の集合に入れていた。順序を変えて試すのは欠損のある文書の式だけで、合計行がないとそれは空なので、試行が1回も走らなかった。最初に入った誤った式が値を決め、後の正しい式は矛盾として棄却された
- 対応: v1.1.1: 対訳の式を順序を変えて試す側に入れ、最もよく式を満たした並び順をそのまま次の段階に渡す（最初の修正では値の決まっていない式を次の段階に渡さなくなり、開発シードで数詞正解率が 0.227 → 0.165 に下がったため、こう直した）
- 検証: tests/test_decipher.py::test_parallel_equations_use_consensus_not_first_come。開発シード20個の全条件で v1.1.0 と同じ成績。評価シード180ケース中179ケースで予測が同一、残る1ケース（SOT・合計行なし・シード206）は数詞が 0 → 9語正解（誤答0）に改善

## 30. 不正な分割指定で、評価用の文書が学習に混入した（修正済み）

- 発見: 独立監査（v1.1.1）。再現: train がすべて存在しないID・heldout だけ指定・train が空 のとき heldout の全文書が学習に入り、heldout の評価が0件になった。train と heldout の両方に書いた文書も学習に入った。heldout だけ指定した場合は警告も出なかった。重複した文書IDは、後の文書が前の文書を黙って上書きした
- 原因: sanitize_public() が、有効な train が1つもないと split 全体を空にし、解読器は split が空だと全文書を学習に使っていた。重複IDは文書の辞書で上書きされていた
- 対応: v1.2.0: heldout に指定した文書は、どの組み合わせでも学習に入れない。有効な train がなく heldout だけ有効なら「全文書 − heldout」で学習し、そのことを警告する。指定があって有効なIDが1つもなければ、分割なしとして明示的に警告する。重複IDは名前を付け直して両方の中身を残し、元のIDと同じ側に置く。実際に使った分割を予測の split_used に記録する
- 検証: tests/test_audit_v12.py の分割に関する7件（修正前のコードでは条件4件・重複・記録・無効分割で失敗）。正しい分割の入力では予測は変わらない

## 31. 外部コーパスの採点で、事前に与えた既知語を推定した語の正解に数えていた（修正済み）

- 発見: 独立監査（v1.1.1）。gpt6-blind-01 の「語彙26語すべて正解」のうち5語は、意味を既知語として与えた語だった（推定した語は21語、判定不能4語）
- 原因: 外部コーパス用の採点（語彙表だけの経路）が既知語を区別していなかった。内部テスト用の採点（トークン単位）は除外しており、2つの経路で扱いがずれていた

- 検証: results/vision/join-sweep-dev.json・join-sweep-val.json（選択）、methods-test-v2.json（最終評価、1回だけ）、docs/VISION_EVAL_V2.md

## 71. 評価器: 予測の行が1つもない画像の行 F1 が「測定不能」になり、集計の平均から消えた（修正済み）。baseline の ARI の平均も、検出0の画像を除いていたことを明記（修正済み）

- 発見: Codex の独立レビュー（PR #11）。#67 の修正で、確認済みの行があるのに予測の行が0件の画像も行 F1 が「測定不能」になり、_agg が文字列を除くため、行の検出に完全に失敗した画像が平均の分母から消えて方式の比較が過大評価になりうる。調べたところ、記録済みの結果（methods-test-v2・val-v2 など）は #67 の修正前に作ったもので、行 F1 は全画像（test 320 枚・val 160 枚）で数えられており影響はなかった。一方、同じ仕組みで baseline の ARI が noise 条件の検出0の画像（test 40 枚・val 20 枚）を除いた平均（0.775、280 枚）になっていて、報告書の表に枚数が出ていなかった
