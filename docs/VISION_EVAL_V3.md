# 画像認識の評価 v3: 行の過剰分割の原因と、新しい行認識（improved-v3）

このファイルは `python -m babel.vision_eval.report_v3` が results/vision/v3/ の JSON から生成する。v1・v2 の記録（docs/VISION_EVAL.md、docs/VISION_EVAL_V2.md、results/vision/*.json）は上書きしていない。

問い: **BABEL が実画像で行を過剰に分割する原因は何か。その誤りを直すと、未知文字の構造解析は本当に改善するのか。**

## 1. 過剰分割の原因

### コードから分かること（babel/vision/recognizers.py の segment_components、improved・improved-v2 が使う）

1. 尺度は「すべての連結成分の高さの中央値」`med_h`。点・短い線・字の部品・雑音の破片も1成分として数える
2. 高さが `0.35 × med_h` 以上の成分は「大きな成分」として、縦の中心の順に並べ、行の中心（それまでの成分の平均）から `0.6 × med_h` より離れると**新しい行を始める**
3. 「小さな成分」（高さ `0.35 × med_h` 未満）だけが、近い行に付けられる。小さな成分は行を作らない

この作りでは、1つの字が上下に離れた部品からなるとき、(a) 部品が多いほど `med_h` が字の高さより小さくなり、(b) 上の部品と下の部品は縦の中心が違うので、`0.6 × med_h` を超えて別の行になる。字の高さが `med_h` の2倍あれば、同じ行の上半分と下半分が2行に分かれる（行数がほぼ2倍になる）。

- 現行の尺度は、正解の字の高さの平均 0.65 倍（上下に分かれた字 stack では 0.39 倍）しかない
- 行のまとめ方を変えず、尺度だけを正解の字の高さに替えると、余分な行は 1 枚あたり 10.77 → 2.40（78% 減）。**過剰分割の大部分は尺度の過小評価による**
- 残り（2.40/枚）は、尺度が正しくても縦の中心だけでは同じ行にできない部品（字の上下の記号、上に伸びる字・下に伸びる字の部品）による。diacritic・tight・mixed に集中する
- 余分な行 10.77/枚 の内訳: 本体の行にも部品がある字の部品だけでできた行（字が上下に裂けた）6.73（63%）、一部がそうである行 3.13（29%）、字が丸ごと別の行になったもの 0.91（8%）
- 尺度を字の大きさ S（成分の max(幅, 高さ) の、インク量で重みを付けた中央値）に替えるだけでは 4.75/枚 が残る（S も、上下に分かれた字では字の高さより小さい）。さらに行の中心からの許容幅も広げると大きく減るが、誤結合が増え、複合方式の誤りの約2〜3倍が残る（第3節の A'）

**結論（人工画像での再現の範囲で）**: 原因は「縦の中心だけで行を決めること」単独ではなく、**小さな部品に引きずられた尺度（成分の高さの中央値）と、縦の中心による行の開始の組み合わせ**。依頼にあった仮説（縦の中心だけを重視する処理）は、半分だけ当たっている。

実画像の 13 → 25 行（左 9 → 17、右 4 → 8）は「ほぼすべての行が2つに分かれた」数で、この仕組み（上の部品の行と下の部品の行）と矛盾しない。ただし画像で確かめていないので、**実画像の原因としては仮説のまま**。

### 試して採用しなかったもの

- **字の列がそろっているかで帯をまとめる条件**: 上下に分かれた字の上の部品と下の部品は同じ列にあるので、帯どうしの列のそろい方を条件に加えた。dev では、条件を外しても（align 0.0）結果が同じだった（results/vision/v3/hybrid-sweep-dev-1-alignment.json。この試行のときの閾値の名前は gap_aligned・align。評価器の修正 #75 の前の指標による記録で、条件を外したコードなので再計算していない）。同じ書き出しの行が続くと別々の行でも列がそろうので、区別に使えなかった。条件は入れていない

## 8. 問いへの答え

### BABEL が行を過剰に分割する原因は何か

- **人工画像で再現し、確かめたこと**: improved・improved-v2 の行のまとめ方は、尺度に「すべての成分の高さの中央値」を使い、その 0.6 倍より縦の中心が離れた成分で新しい行を始める。字が複数の部品からなると尺度が字の高さより小さくなり（dev の平均で 0.65 倍）、同じ行の上の部品と下の部品が別の行になる。尺度だけを正解の字の高さに替えると余分な行の約8割が消える（第1節）
- **実画像（IMG_4494）について**: 画像がないので確かめていない。25行 ≒ 13行 × 2 という数は上の仕組みと矛盾しないが、仮説のまま

### その誤りを直すと、構造解析は本当に改善するのか

**人工画像では、改善する。ただし正解の転写には届かず、行を詰めた画像では直りきっていない。**

- 行認識（holdout、開発に使っていない字の作りと劣化）: 余分な行 26.28 → 0.74/枚、誤結合 2.56 → 0.47/枚、行 F1 0.436 → 0.945
- 記号の検出（holdout）: F1 0.364 → 0.881。行が正しくまとまると、同じ行に入った上下の部品が1つの字に結合されるため。字の分割は 75.7 → 2.3/枚
- 構造解析（13行）: 発見した規則は improved-v2 0.81 → improved-v3 2.88（正解の転写 4.50、/8）。偽の仮説は 19.0 → 4.0（正解の転写 0.5）。仮説の数は 21.2 → 17.4 に**減った**（増えたのは正しい仮説 1.0 → 11.5）
  - 行境界の誤りだけを正解の転写に加えると（13行）: 各行を2つに分けると発見 4.50 → 3.33（行境界に依存する規則 3.50 → 2.00）、偽の仮説 0.5 → 2.3。2行を1つにまとめると発見 2.67、偽の仮説 4.5
- 構造解析（30行）: 発見した規則は improved-v2 0.97 → improved-v3 3.65（正解の転写 5.00、/8）。偽の仮説は 56.8 → 12.4（正解の転写 0.2）。仮説の数は 61.6 → 45.2 に**減った**（増えたのは正しい仮説 2.5 → 30.0）
  - 行境界の誤りだけを正解の転写に加えると（30行）: 各行を2つに分けると発見 5.00 → 4.00（行境界に依存する規則 4.00 → 2.00）、偽の仮説 0.2 → 7.8。2行を1つにまとめると発見 3.17、偽の仮説 17.7
- 同じ画像での比較（144 枚）: improved-v3 の方が発見した規則が多い画像 126、少ない画像 3、同じ 15
- 改善の中身は2つが混ざっている: 行境界が正しくなったこと（行境界に依存する規則が増えた）と、上下の部品が1つの字にまとまって記号そのものが正しくなったこと（それ以外の規則も増え、対応しない記号を含む偽の仮説が減った）。正解の転写の行だけを壊す実験（L-split）での低下は発見 1 件前後なので、improved-v2 の低下の大部分は、行の分割に伴って字が破片になることによると考えられる（2つを完全に分ける実験はしていないので、推測）
- 単語境界（合議）の F1 は 13行で 0.194 → 0.283（正解の転写 0.316）、30行で 0.205 → 0.287（正解の転写 0.365）
- 仮説の安定性（部分標本・転写の攪乱での再現率）は、方式の間でほとんど変わらない（表）。安定性は、仮説が正しいかどうかを区別していない

### 副作用

- **字の誤結合が少し増えた**（holdout、同じ画像で improved-v2 より多い 55 枚・少ない 17 枚、平均 +1.72/枚）。同じ行に入った別の字が、横に重なると1つにまとめられる
- **クラスの構造（ARI）は改善していない**（holdout、差の平均 -0.004、良い 79 枚・悪い 103 枚）。ARI は検出で対応した記号だけで計算するので、検出が増えた分だけ難しい記号が評価に入る。分類の方式は変えていない
- **行を詰めた画像（tight）では誤結合が残る**: holdout で誤結合 2.50/枚、行 F1 0.69、検出 F1 0.50。隣の行と上下の範囲が重なると、投影の谷が浅くなって行が切れない
- 処理時間は improved-v2 と同程度（holdout で 0.067 → 0.067 秒/枚、既存の test で 0.055 → 0.065 秒/枚）
- 既存の評価画像（行の間隔が一定）では悪化なし。改善も小さい（第5節）。**行の作りが単純な画像では、v2 と v3 の差はほとんどない**

### 単純な修正で足りるか

- 現行方式の尺度を S に替え、許容幅を広げるだけ（A'）で、行の誤り（余分な行＋誤結合）は dev で 11.96 → 1.44/枚、val で 1.22/枚になる。複合方式（E）は dev 0.79・val 0.61/枚
- 過剰分割の大部分は単純な修正で直る。複合方式を選んだのは、同じ基準（行の誤りの合計）で dev・val とも最も良かったから。A' は誤結合と字の結合が多い（第3節の表）

## 9. 限界と残る問題

- **実画像では何も測っていない。** 人工画像の字の作り・劣化は5種類の生成方法によるもので、実際の筆写・写真・画面の写しを代表しない。holdout も同じ生成器の別の設定で、行の並べ方の規則は dev と共通
- holdout の improved-v2 の過剰分割（行数が正解の 3.7 倍）は、依頼にあった実画像の値（約 1.9 倍）より大きい。holdout の字は部品が多いためで、**改善の大きさは字の作りに依存する**。実画像での改善の大きさは分からない
- 新方式は「行と行の間の空きが、1つの字の中の部品の上下の隙間より大きい」ことを前提にする（join_gap × S が境目）。行の間が字の部品の隙間と同じくらい詰まった文字体系では、別の行をまとめる。逆に、部品の隙間が大きい字は分かれる
- 字の大きさ S は、上下に分かれた字では字の高さの 0.4〜0.8 倍になる。S に対する比で決めた閾値は、字の作りによって実質の値が変わる
- 行が傾いている・曲がっている画像は、横向きの投影を使うので弱いはず。photo の傾きは 0.3〜0.8 度だけで、それ以上は試していない
- 縦書き、行の途中で字の大きさが大きく変わる画像、領域の指定なしで段組みを分けることは扱っていない（two_column は領域の枠を認識器に渡している。実画像の評価でも領域は人が指定する）
- 小さな部品（点・短い線）だけでできた字は、近い行の字に付けられる。小さな部品だけの行は検出できない
- 構造解析の採点は人工言語 regular の設計した8規則だけ。実際の未知言語の規則がこれに似ている保証はない。正解の転写でも 13 行で 4.5/8 しか見つからない（データ量と構造解析の限界: docs/ISSUES.md #41・#45）
- improved-v3 でも偽の仮説は正解の転写より多い（13行で 4.0 対 0.5）。認識の誤りが残る限り、仮説は画像と照合して確かめる必要がある
