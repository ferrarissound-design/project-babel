# 認識の誤りに強い構造検定: 本当にある構造と、認識の誤りが作った構造を区別できるか

このファイルは `python -m babel.robust_eval.report` が results/robust/ の JSON から生成する。既存の記録（docs/VISION_EVAL*.md、results/vision/、results/structure/）と既存の認識方式・構造解析のコードは変えていない。

評価単位は画像ごとに独立した本文。同じ切り出しを共有する再分類は1票として集約した。陰性対照の『報告率』は仕込みのない画像での検出であり、偶然生じた実際の類似を含むため、純粋な誤検出率ではない。正解転写で有意な組のない画像の率も併記する。閾値の採用には報告率の Wilson 95% 上限を使う。

**評価上の注意**: 結合行の誤採点を v2 の holdout 結果を見た後に修正した。ここに示す v3 の holdout は事後再分析であり、新しい初見データでの検証ではない。

問い: **PROJECT BABEL は、未知の文字列から、本当に存在する構造と、画像認識の誤りが生み出した見かけ上の構造を区別できるのか。**

**測ったこと**

1. ### 2.2 原因: 既存の検定は、記号1つの取り違えで切れる

既存の検定は、2つの行が共有する**連続した** 2〜4 記号列の数を数える。2つの転写を位置ごとに対応させて（2.4）、同じ行の組を見比べた:

**行 (3, 4)**（共有する 2〜4 記号列: baseline 3 種、improved-v3 0 種。既存の検定は 2 種以上を要する）

- baseline: `18 19 20 21 22 23 24 25` / `26 19 27 21 22 23 28`
- improved-v3: `19 20 21 22 23 24 25 26` / `27 20 28 28 22 29 24 26`
- baseline が「2行に共通」とみなした 4 記号を improved-v3 で見ると: 19→同じ、21→同じ、22→**別のクラス**、23→同じ
- improved-v3 が「2行に共通」とみなした 4 記号を baseline で見ると: 20→同じ、22→同じ、24→同じ、26→**別のクラス**

**行 (0, 1)**（共有する 2〜4 記号列: baseline 1 種、improved-v3 6 種。既存の検定は 2 種以上を要する）

- baseline: `0 1 2 3 4 5 6` / `0 1 7 3 8 9 10`
- improved-v3: `0 1 2 3 2 4 5` / `0 1 2 3 6 7 8`
- baseline が「2行に共通」とみなした 3 記号を improved-v3 で見ると: 0→同じ、1→同じ、3→同じ
- improved-v3 が「2行に共通」とみなした 4 記号を baseline で見ると: 0→同じ、1→同じ、2→**別のクラス**、3→同じ

どちらの組も、2つの転写は共通の記号 4 個のうち 3 個で一致し、1 個で食い違う。その1個が連続した記号列の途中にあると、共有する記号列が 0〜1 種になって既存の検定の下限（2 種）を割る。**規則が入れ替わったのではなく、同じ2組の規則が、転写ごとに別の1記号で切れていた。**

### 2.4 2つの転写は、どの位置を「同じ記号」とみなしたか

クラス番号は転写ごとに別なので、番号ではなく「同じ記号とみなした位置の組」を比べた。長さが同じ行（6 行）は位置ごとに1対1と**仮定**し、ほかの行はそこで学んだクラスの対応を手掛かりに推定した。

| 範囲 | 位置の組 | 両方が同じ | baseline だけが同じ | improved-v3 だけが同じ | 調整ランド指数 |
|---|---:|---:|---:|---:|---:|
| 長さが同じ行だけ | 1275 | 13 | 3 | 22 | 0.5012 |
| 全行（推定の対応を含む） | 4465 | 35 | 7 | 55 | 0.5242 |

- 一方の1記号がもう一方の2記号に当たる箇所が 14（推定）。問題1の「一方を1記号、もう一方を複数記号」に当たる。どちらが正しいかは画像がないと分からない

### 2.5 この節から言えること・言えないこと

- 言える: 行 0・1 と行 3・4 の類似は、3本の転写のどれでも見える。「方式を変えたら規則が変わった」のは検定の作りによる
- 言えない: この2組が画像に本当にあるか。3本の転写は同じ画像・同じ二値化の系統から作られていて、共通の誤りを除けない。また、**新しい統計量は、この転写を見てから選んだ**（最初に試した1つで、その後は変えていない）。実データでの p 値は探索的なものとして読むこと。統計量の妥当性（誤報告の率）と検出力は、この転写と無関係な人工データで測った（第5・6節）
- 言えない: 2組の意味。同じ書き出しの2行、同じ枠の2行という以上のことは分からない

## 3. 方法

### 3.1 行の組の類似の検定（babel/robust/rowsim.py）

- 統計量: 2つの行の、順序を保って対応する記号の数の最大値（最長共通部分列の長さ）。記号の取り違え・抜け・余分があっても、残りの一致を数える
- 帰無モデル: 全体シャッフル（行の長さを保ち、全記号の位置を入れ替える）。既存の linepair 族と同じ
- 多重検定: 組ごとに置換分布で標準化し、行の組すべての最大値の置換分布と比べる（Westfall–Young の maxT）。「1つでも誤って有意とする確率」を制御する
- 支持の下限: 一致が 3 記号未満の組は報告しない
- 標準ライブラリだけで動く（NumPy があれば置換をまとめて計算する。同じ値になることをテストで確かめている）

### 3.2 認識方式の集まりと票（babel/robust/ensemble.py）

1枚の画像を 8 通りに転写し、方式ごとに 3.1 の検定を行う。仮説は、行の枠の上下の重なりで基準の方式（improved-v3）の行に対応させる（クラス番号は使わない）。ある行の組が何個の方式で有意かを「票」とする。

| 方式 | 切り出し | 分類 | 変えたもの |
|---|---|---|---|
| v3 | improved-v3 | template（閾値 0.20） | 基準 |
| v3-fine | 同じ | template（閾値 0.12） | 分類を細かく |
| v3-coarse | 同じ | template（閾値 0.30） | 分類を粗く |
| v3-shape | 同じ | shape（特徴量） | 分類の方式 |
| v3-iou | 同じ | iou（baseline の分類） | 分類の方式 |
| v3-scaled | improved-v3（画像を 1.3 倍） | template | 画像の大きさ |
| v2 | improved-v2（行のまとめ方が旧方式） | template | 行のまとめ方 |
| baseline | 投影 | iou | 切り出しと分類の両方 |

構成は dev の結果を見る前に決め、その後は変えていない。既存の方式（METHODS）は書き換えず、同じ部品を呼ぶだけ（テストで確かめている）。

### 3.3 分類を経ない検定（不採用）

記号をクラスに分けず、字形の類似度（0〜1）を重みにして同じ検定を行う方式も作った。分類の閾値の近くで「同じ」と「違う」に倒れるのを避ける狙い。dev では、クラスの一致による検定より良くならなかった（第5節）ので、判定には使っていない。

### 3.4 dev だけで選んだもの（results/robust/selected.json）

- 票の閾値: 規則は「仕込みのない dev 画像の報告率の Wilson 95% 上限が 0.05 以下になる最小の k」。結果は **k = 3**
- 分類を経ない検定の tau: 規則は「同じ上限を満たす候補のうち発見率が最大」。満たす候補がなく、**不採用**
- 独立レビュー後、本文の独立性・票の依存性・閾値の不確実性を修正し、dev を再実行して選択した。旧 dev 結果と旧閾値を使い回していない。holdout では選び直さない

## 4. 評価データ（babel/robust_eval/）

| 分割 | 字 | 行の作り・劣化 | シード | 画像 | 用途 |
|---|---|---|---|---:|---|
| dev | font・stroke・stack | plain・diacritic・tight・mixed | 100〜107 | 576 | 方式の設計、閾値の選択 |
| holdout-synth | radical・curve | plain・diacritic・tight・mixed・photo | 9100〜9109 | 600 | 閾値を固定してから1回だけ |

- 文（texts.py）: IMG_4494 の転写と同じ規模（13 行、行の長さ 6〜13）。語彙 30・80・250 の Zipf 分布から引く。**仕込みあり**の文は 2 組の行に類似を仕込む（一方を写し、各位置を 15〜45% の確率で別の記号に替え、ときどき1記号を抜くか足す）。**仕込みなし**の文は陰性対照。各分割の半分ずつ
- dev の字は babel/vision_eval/layout.py の font・stroke・stack。holdout-synth は dev に出ない字の作り（radical・curve）と劣化（photo）
- holdout-font は、**実在の文字体系を実在のフォントで描いた画像**（realfont.py: グルジア文字・アルメニア文字・タイ文字・片仮名・平仮名・漢字・ハングル、アンチエイリアスあり、degraded はぼかしと JPEG）。字形の設計に、このリポジトリの作者が関わっていない。ただし実画像（写真・手書き）の代わりにはならない

- 認識器には画像（と領域の枠）だけを渡す。babel/robust は正解・評価用のコードを import しない（テストで確かめている）
- **holdout について開発中に見たもの**: realfont の描画が正しいかを確かめるために、シード 1 の画像 5 枚（グルジア・タイ・片仮名・漢字・ハングル）で baseline・improved-v2・improved-v3 の認識の指標（記号数・検出 F1・ARI）を見た。行の組の検定は走らせていない。評価のシード（9200〜）とは別

## 9. うまくいかなかったこと・評価の欠陥の検討

| 何をしたか | 何が起きたか | どうしたか |
|---|---|---|
| 多重検定の補正を minP（最小 p 値の置換分布）で実装した | 統計量が整数で置換回数が 999 だと、補正後の p 値の下限が 0.02 前後になり、行の多い転写（improved-v2 の 25 行）では有意水準に届かないことがあった | 標準化した統計量の maxT に替えた（dev を走らせる前） |
| 予測の行を、IoU 0.5 以上で対応する正解の記号から正解の行に戻した | 字の破片だけの行は正解の行に戻せず、全部「偽」と数えられた（仕込んだ行の破片どうしの類似も偽になり、認識の誤りによる偽を多く見積もる） | 重なる面積が最大の正解の記号の行に戻すように替えた（dev を走らせる前） |
| 新しい検定を1つの転写に使う | 仕込みのない画像での誤報告が名目 0.05 を超えた（improved-v3 で dev 0.069）。置換検定は「記号の位置が入れ替え可能」を前提にするが、認識の誤りは行ごとに偏る（行の誤結合、字の部品の行）ので前提が崩れる | 単独では使わず、方式の集まりの票と組み合わせる。単独の結果は「候補」と呼ぶ |
| 分類を経ない検定（字形の類似度を重みにする） | dev で、クラスの一致による検定と発見率・誤報告が変わらなかった。見落としの主因は分類の閾値ではなく、切り出しと行の誤り | 不採用（選択の規則どおり）。コードは残し、参考として出すだけ |
| 分類方式どうしの一致から、分類の精度を正解なしで見積もる | 正解との一致との相関が弱かった（第8節） | 指標として使わない |
| 2つの方式で見つかる組の集合の一致を、新しい検定で上げる | 上がらなかった（第7.3節） | 「検定を替えれば方式に依存しなくなる」とは言わない |

評価そのものの限界:

- **正解の定義**: 「真」は仕込んだ組。仕込んでいない組が偶然似ることがあり（正解の転写でも 5% 前後の文で1組が有意）、それは認識の誤りではないが偽に数えている
- **方式の集まりの偏り**: 8 方式は3つの切り出し群に集約した。同じ群の再分類は独立した票に数えないが、前処理や画像そのものを共有するため、3群も完全に独立ではない。手書き資料での精度は未検証
- **仕込んだ構造は1種類**（同じ枠の行の組）。位置の規則・連接・共起など、ほかの族の仮説には票の方法を使っていない
- **人工画像と実在のフォントの画像は、同じ字が画素までほぼ同じ**。手書き・写真・劣化した資料では、分類の誤りがずっと多いはずで、ここでの数値は当てはまらない
- **統計量を実データを見てから選んだ**（第2.5節）

## 10. 5つの問題への答え

**問題1（同じように見える記号が、異なるものとして認識される）** — 一部だけ分かった。baseline と improved-v3 は、対応が付いた位置の組のうち 25 組（長さが同じ行だけで）について「同じ／違う」が食い違い、1記号と2記号が対応する箇所が 14 ある。食い違いの場所は compare-baseline-v3.md に列挙した。**どちらが字形の違いで、どちらが認識器の誤りかは、画像がないので確定していない。** 人が見るべき位置は絞れた

**問題2（認識方式によって構造仮説が変わる）** — 原因を特定した（第2.2節）。既存の検定が、記号1つの取り違えで切れるため。切れない検定では、行 0・1 と行 3・4 の2組が、どの転写でも有意。ただし「画像に本当にある」ことの確認には画像が要る

**問題3（視覚クラスの分類が不安定）** — 未確定（第8節）。認識器の「1回だけのクラス」には分けすぎが混ざること、2方式の一致でも分けすぎを否定できないことを、正解つきの画像で示した

**問題4（人工データと実画像の性能差）** — 未検証。切り出し群（3/3 以上）の dev は、発見率 0.18・仕込みなし画像の報告率 0.004。holdout は dev に出ない字の作りと劣化（holdout-synth）で発見率 0.11・誤報告 0.01。実画像（写真・手書き）への一般化は測っていない。実画像の正解転写が1枚もないため

**問題5（構造を発見しても意味には到達していない）** — 到達していない。この研究が足したのは「見つかった構造が認識の誤りによるものかどうか」の判定で、構造の種類（文法・定型句・見た目の繰り返し）は区別していない。行の組の類似は、同じ枠の文でも、箇条書きの記号でも、画面の飾りの繰り返しでも同じように出る。13 行・119 記号では、どれであるかを統計で決めるだけの量がない。区別するには、(a) 画像そのもの（文字か飾りかは見れば分かることが多い）、(b) 同じ資料の続き（枠が別の行にも現れるか）、(c) 文脈や対訳、のどれかが要る

## 11. 最終の問いへの答えと、反証の条件

**答え: dev では検討できる。holdout と実画像での検証が必要。**

- 1つの転写からは、できない。認識の誤りは、置換検定で有意になる構造を作る（仕込みのない画像の 48%〔improved-v2〕、7%〔improved-v3〕で、dev）。既存の安定性の指標も、それを見分けない
- 同じ画像を複数の方式で転写し、切り出し群をまたいで再現する規則を採る候補がある（行の組の類似について、3/3 以上で、報告のうち仕込んだ組が 0.98 / 0.94）。1群でしか出ない規則も真の可能性があるため、画像で照合する
- ただし「方式をまたいで再現する」は「画像に本当にある」の近似で、どの方式にも共通する誤りは見分けられない。また「画像に本当にある」は「言語の構造である」を意味しない

**この答えが誤りだと分かる条件**

1. 再設計後に固定した予測が、新しい holdout（別のシード・別の字）で外れる
2. 実画像の正解転写ができたとき、票 3/3 以上の行の組が、正解の転写での検定で有意でない
3. IMG_4494 の画像で `babel robust-structure` を走らせたとき、行 0・1 と行 3・4 が閾値に届かない。その場合、第2節の「どの転写でも有意」は、baseline と improved-v3 に共通する誤りによるものだったことになる
4. 人が画像で行 3・4 の対応する記号を見比べて、同じ字ではないと判断する

**足りないもの（これがあれば解決できること）**

| 足りないもの | あれば分かること |
|---|---|
| IMG_4494 の画像 | 2組の規則が方式をまたいで再現するか（上の条件 3）。食い違う位置の字形を直接見比べられる |
| IMG_4494 の正解転写（人が確かめたもの。docs/GROUND_TRUTH.md の手順） | 問題1・3 の確定（どちらの方式が正しいか、1回だけのクラスが本物か）。問題4 の実画像での精度 |
| 別の実画像と正解転写 | 実画像への一般化。今は 0 枚 |
| 同じ資料の続き・文脈 | 問題5（構造の種類と意味） |
